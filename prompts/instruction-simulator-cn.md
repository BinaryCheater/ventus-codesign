# 完善 Ventus 通用指令级性能模拟器

在当前独立的 `ventus-codesign` 仓库继续工作。先读 AGENTS.md、README.md、docs/status.md、docs/model.md、docs/workflows.md 和 docs/project_tasks_cn.md，检查已有修改。直接实现，不停留在方案。本文更新此前“接入 Qwen”的实现方向：以通用程序输入和硬件时序为主，Qwen 是完整 workload 验收案例。

## 目标与边界

保留并完善现有指令时序后端，接收实际程序的指令、寄存器依赖、访存地址、访问宽度、线程掩码、同步和 kernel 资源信息。模拟器不计算全部张量数值，不需要生成文本。

不要继续添加按网络名称或算子名称选择耗时公式的模板。已有 GPT-2 程序生成器可保留作测试；不要将改过尺寸的 GPT-2 图称为 Qwen。此前撤回的 Qwen 模板和改变调度语义的原生执行器不作为已完成的基础。

不做 ChiselSim 迁移，不新增 RTL 实测，不以全面修复官方 SystemC 模型为前置任务。复用现有源码和实验记录；能定位的程序/模型问题直接修复。

## 程序入口

建立这条路径：软件实现及映射 → 官方 Ventus 编译器 → 编译程序与启动描述 → 动态指令提供器 → 参数化时序核心。

优先复用官方 kernel、编译器、解码和功能执行能力。调查匹配的分支和版本，不仅看上游默认 main。可用 Spike 或经过检查的 CModel 提供分支、mask 和实际访存信息，不能用其周期数拟合我们的时序。

用轻量运行器组织真实 kernel 调用、参数、缓冲分配、别名、数据依赖、同步与跨 kernel 状态。无需把整个 PyTorch fork 接进每次评估。以官方 PyTorch 后端的 kernel 与调用行为为来源，并核对所有隐式转换/拷贝及可能的 CPU fallback；未支持的设备工作明确报告，不能悄悄丢掉。

规则循环可用可执行的地址/指令生成器或压缩记录表示，但要与编译程序对应。不要把总 FLOPs 或总字节数作为唯一输入。按 warp 保留程序顺序和同步，跨 warp/SM 交错由时序后端决定。硬件改变时，禁止重放固定的旧全局调度顺序。

软件变体改变算法、tile、融合、布局或工作分配时，更新编译产物、动态行为和资源元数据。兼容的软件程序扫描硬件参数无需重复编译；影响指令形状、线程组织或 ABI 的配置变化要重新生成匹配程序。

## 指令和资源覆盖

先从实际编译产物列出缺失的指令清单，再完善 IR 与执行机制。重点包括 BF16/FP16/TF32 MMA、转换、打包计算、需要的 SFU 指令、访存宽度、寄存器组读写、控制流/SIMT 和同步。kernel 元数据必须反映寄存器、LDS、warp/block 需求。

保留 RF bank/port、collector、scoreboard、共享计算流水线、背压、LSU、LDS bank 冲突、cache/MSHR 和外存并发等现有机制。资源容量和吞吐改变应真实影响执行，不能只改变日志里的参数。

核对官方低精度指令与当前固定 RTL/ISA 的对应关系。未取得时序依据的参数集中、显式管理，不随意把旧 FP32 Tensor 规则套成 BF16。成本未覆盖时返回清楚的状态，不阻止性能接入，也不伪造预算可行性。

## 执行速度

按前次审计方向实现 Rust 时序核心，重点消除逐周期全量扫描、字符串/字典处理和大量临时事件。采用紧凑指令、就绪队列、事件跳转和流式输入。迁移时与现有执行器比较周期、计数和状态，先保持语义，再做有明确依据的改进。

重复段可以压缩，但复用条件必须包含影响结果的地址映射、cache/队列/依赖等状态。不能简单把一层耗时乘层数，不能逐 kernel 重置 cache，也不能用串行化所有指令来换取实现简单。只保留搜索所需统计，详细 trace 按需开启。

本轮允许小程序回归及实际 workload 的运行时间测量；不做新的 RTL、ChiselSim 或 SystemC 性能基准。先完成一个真实 kernel 的两种软件变体，再跑一个完整 Qwen 场景、优化瓶颈，继续覆盖其余场景。

## 验收案例

最重要的通用性检查：同一计算提供两种真实软件实现，例如不同 tile/布局或融合前后。只更换程序和启动描述，不改模拟器代码，能看到指令、访存、占用和周期变化。再改变硬件参数，确认对应服务能力确实变化。

完整场景按 docs/project_tasks_cn.md：Qwen2.5-0.5B-Instruct，batch=1，prefill 128/512；初始上下文 128/512 后分别 decode 16 步。固定 token 序列，明确冷 cache 和已有外存 KV 的初始条件。包括最终 LM head；按生成语义区分 prefill 中需要计算 logits 的位置。小型同结构案例用于调试，不能代替完整模型交付。

将 GPT-2 作为第二个程序组织案例，并增加官方 Pythia-410m-deduped 的 FP16 prefill 128/512，复用同一指令接口与时序核心。Pythia 的并行残差与部分 RoPE 按真实程序处理，不套用 GPT-2 图；首轮不要求其 KV decode。若尚未完成，列出具体未支持指令或入口，不能笼统声称所有 Transformer 已支持。Diffusion 目前仅为任务文档的扩展方向，本轮不要求另做模型移植。

覆盖形状、地址、依赖、指令覆盖、计算和搬运工作量、KV 追加、资源分配及硬件参数生效的测试。保留失败结果，修复后重评；不要求每个参数增加都必然带来加速。

## 交付

提供通过现有 `./run` 调用的统一入口，输入场景、硬件、软件配置及新结果目录。保存版本/程序/配置标识、完成状态、总周期、分阶段和逐 decode 步周期、关键资源计数、宿主耗时及峰值内存。

复用构建缓存。长任务恢复必须保留完整必要状态，不能只记住层号后清空存储状态。若实现不了完整恢复，就明确只支持重新运行，避免错误续算。

更新 docs/status.md、docs/model.md、docs/workflows.md 和相关验证说明；用真实可运行命令替换任务文档中尚未发布的入口说明，保留其任务目标和场景。不要自行改变学生的 workload、预算或评价指标。

遵守忽略的私有配置及原有默认服务器执行方式，不向共享文件写入个人地址。不要修改原父项目，不覆盖历史结果，不自动推送。运行相关回归、ruff check、ruff format --check 和 pytest。

最终报告已完成的通用入口、实际指令覆盖、两种软件变体的对比、完整 Qwen 场景的实测宿主耗时及剩余具体问题。不要把模板原型或未完成的运行当作完整接入。

## 当前实验约定

以 docs/baseline_cn.md 与 examples/project-baseline-v2.json 为准。固定多精度目标，不新增切换罚时或要求新 RTL；显式转换/搬运仍计时。主任务为四个 Qwen 场景，GPT-2/Pythia 完整入口是后续扩展。使用统一总面积预算，无独立总 bits 上限；保持现有执行默认位置。
